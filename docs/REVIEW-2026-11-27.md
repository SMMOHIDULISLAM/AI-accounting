# AI Accounting review — 27 November 2026

## Assessment

The web app is a working small local ledger foundation. It is not yet the complete WhatsApp-operated product. This release adds a tested first intake path and fixes reproducible data-safety defects. Live connection, memo reading and all operations inside WhatsApp still need implementation/configuration and real delivery evidence.

The original web `db.ts` and README in the supplied archive exactly matched GitHub `main` at `40910e4662e12c9d78a2fc4702c4b4bde95f42a9`. Each `(1)`/un-numbered ZIP pair was byte-identical; the two storage-verification ZIPs were also identical. They were not separate versions. The Android archive is a separate app and was reviewed as source/evidence, not merged or newly certified by this release. Plans and instructions inside the supplied documents were treated as historical context.

## Findings corrected

| Finding | Reproducible consequence | Correction |
|---|---|---|
| Backup skipped pending writes | Calling save and then backup without awaiting save could export an earlier ledger | Serialize backups with writes; test inclusion of earlier saves and exclusion of later saves |
| Unsafe journal sums | Distinct totals rounded to the same JavaScript number, permitting unbalanced posting | Safe-integer sums, reject unsafe posted totals during restore |
| Report aggregate overflow | Large posted totals were silently rounded | Bound all report arithmetic; render an explicit failure while keeping records/backups available |
| Decimal formatting/edit/export drift | MAX_SAFE_INTEGER minor units displayed with the last cent wrong | Exact decimal text in display, editor, CSV preview and reports |
| Altered backup schema accepted | A backup could introduce a trigger that changes later ledger writes | Require canonical web v1 table/index/trigger structure before accepting data |
| UTC used as “today” | Early local-day entries could receive the previous UTC date | Use device-local calendar dates; incoming messages use the configured business timezone |
| Test environment conflicts | Node 24 Web Locks conflicted with isolated host test ledgers; AI tests assumed exclusive port 11434 | Keep lifetime locks browser-only and await release; inject AI transport and use ephemeral HTTP ports |
| Vulnerable dependencies | Initial npm audit flagged nine dependency entries including high/critical development-tool findings | Update Express, Vite/Vitest and selected runtime packages; both installed and pnpm-lock audits report zero known vulnerabilities at review time |
| WASM version coupling | Updating sql.js while serving the old public binary can break initialization | Generate WASM from the installed package before dev/build instead of committing a stale binary |

CSV exports also escape formulas with leading whitespace while preserving validated signed decimal text. Default Vite host validation is restored instead of allowing arbitrary hostnames.

## WhatsApp intake delivered

`sale cash 100 bdt, credit 50 bdt` produces a draft with Cash Dr 100, Receivables Dr 50, Sales Cr 150 BDT. Bengali labels/digits also work. This is an explicit rules parser, not a claim of free-form AI comprehension. Original messages remain in the intake queue. No tax or inventory entries are invented.

The server validates signatures against raw bytes, checks Business account and phone ID, filters sender numbers, persists messages transactionally and deduplicates WhatsApp message IDs. A separate authenticated browser inbox imports drafts idempotently. Replayed messages cannot overwrite posted entries. No live customer messages or owner ledger were used in testing.

Receipt media metadata is retained; image/PDF bytes are not downloaded or read. Attachment intake is not OCR or durable receipt storage. No WhatsApp reply bot, conversational confirmation or background posting exists. See [WHATSAPP.md](WHATSAPP.md).

## Evidence and limits

- Regression tests demonstrated four original failures before the fixes: unsafe equality, report overflow, last-cent display drift and pending-save omission.
- TypeScript checking and production build pass on Windows with Node 24.20.0.
- Final automated result: **63 passed, 0 failed**. The production HTTP smoke also passes (health, SPA/bundle, API 404, disabled integration defaults and paired/compilable WASM). Reproduce with `pnpm build` then `pnpm smoke`; see [verification.json](evidence/verification.json).
- The automated suite exercises accounting, SQLite/WASM with fake IndexedDB, signed real-HTTP webhook/intake endpoints, a real host SQLite inbox, authentication, retries, restart persistence, media references, local import and explicit posting.
- The attached original synthetic backup was restored successfully by the hardened web implementation: 15 accounts, 4 journals and 2 sources. This is compatibility evidence for that web fixture, not Android schema compatibility.
- Dependency audits report zero known vulnerabilities at the time checked. This is not a guarantee against undisclosed issues.
- Windows sandbox restrictions blocked pnpm's project symlink creation. Dependencies were installed with npm without lifecycle scripts; pnpm generated and verified the frozen lockfile and audited it. The included GitHub CI workflow checks the normal pnpm install path when run; local evidence does not assert a completed GitHub run.
- Full interactive browser verification was not completed: Computer Use stopped because it could not determine the browser URL confidently. HTTP integration, types, build and automated evidence must not be described as a physical browser/phone pass.
- No real WhatsApp Business setup, outgoing message, public deployment, native APK, physical phone/USB test or local-model inference was performed.

## Remaining product priorities

1. Connect a real Business test number and persistent HTTPS intake server; verify the complete live text path before regular use.
2. Implement receipt retrieval/retention and reviewed OCR with confidence, duplicate checks and tax/total validation.
3. Add named customers, invoice references and settlement matching; today's split sale uses the aggregate receivables account.
4. Design WhatsApp confirm/cancel/replies and supported transaction types. Extend deterministic rules or reviewed AI extraction without autonomous uncertain posting.
5. Decide the authoritative ledger and authentication model for cross-device/WhatsApp-only operation. Current data remains split between an intake server and one designated browser ledger.
6. Reconcile the native v2 and web v1 schemas through an explicit migration, then build/test Android and physical backup workflows. Do not blindly restore one format into the other.

The ledger is single-currency, unencrypted, and intended for draft management bookkeeping. It does not implement jurisdiction-specific taxes, complete statutory reporting, multi-tenant authorization or financial-success guarantees. Source visibility and app-data protection are separate concerns.
